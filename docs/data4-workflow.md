# Pathways ingestion workflows (Drive + OneDrive → `ingest.participants`)

Two importable n8n workflows, both generated by [`scripts/build_data4_workflow.py`](../scripts/build_data4_workflow.py) — edit that script (or the JS under [`scripts/js/`](../scripts/js/)) and re-run `python scripts/build_data4_workflow.py` rather than hand-editing the JSON, so the SQL column lists and the JS parameter arrays that feed them can never drift out of sync. (The file/script names still say "data4" for historical reasons.)

| File | Role |
| --- | --- |
| [`workflows/data4-ingestion.json`](../workflows/data4-ingestion.json) | **Pathways Ingestion** — lists files from Google Drive / OneDrive, drives the load loop, writes per-file bookkeeping. |
| [`workflows/pathways-chunk-loader.json`](../workflows/pathways-chunk-loader.json) | **Pathways Chunk Loader** — loads ONE ~8 MB window of ONE file into the target database. Called by the first workflow; never run by hand. |

## Why it's two workflows (what was breaking)

The first version downloaded the whole file, turned it into one n8n item per row, mapped them in a single Code node, and ran one `INSERT` per row per database. That works for a 49-row workbook and falls over on `20_million_by_2032tbl.csv` (~258 MB, ~871k rows):

- **n8n crashed with `JavaScript heap out of memory`** (2 GB V8 heap): Download held the file in memory, *Extract CSV* built ~871k items, and the old *Limit Rows* cap sat **after** Extract, so it limited nothing that mattered. Every run since the consolidated file appeared left a `crashed` execution.
- **Map Columns timed out** (300 s, and still at 3600 s): it called `$('Tag Source').itemMatching(i)` — a round trip out of the sandbox — once per row, and logged one unmapped-column item per *cell* (~22 unmapped columns × 871k rows ≈ 19M items).
- **Load was hopeless**: ~1.7M single-row queries (871k rows × two databases), and n8n stored ~465 MB of run data per execution.

Now the file is read in ~8 MB **byte ranges**, and each range is loaded by a **sub-workflow**, whose memory (chunk text, row batches) is released the moment it returns. The parent only ever holds a few-KB loop-state item, so memory stays flat no matter how big the file is.

## How it works

```
Manual/Schedule -> Start Run ─┬─> List Consolidated Data Files -> Tag Source -> Keep CSV or XLSX ─┐
                              └─> List OneDrive Files ---------> Tag Source -> Keep ... -> Limit ─┤
                                                                                                    v
                                                                                        Init Load State  (one state item: files, offset, counters)
                                                                                                    v
                                                                              ┌──────────> Load Chunk  (Execute Workflow -> Chunk Loader)
                                                                              │                     ├─> More Work? ── allDone=false ──┘  (loop)
                                                                              │                     ├─> Emit Unmapped Columns -> Insert Unmapped Column Log
                                                                              │                     └─> Emit File Result -> Upsert Drive File State, Insert Ingestion Log, Mark Dashboard Dirty

Chunk Loader:  Plan Request -> Which Source? -> Fetch Range (Google Drive | OneDrive) -> [Is XLSX? -> Extract XLSX Rows] -> Parse Window
                                   -> Insert Participants Batch -> Summarize Window
```

- **Init Load State** collapses every listed file into one state item. Two knobs live at the top of its code: `CHUNK_BYTES` (window size, default 8 MB ≈ 26k rows) and `MAX_ROWS` (`0` = load everything).
- **Fetch Range** does `GET …?alt=media` with a `Range: bytes=start-end` header, using the same OAuth credential as the list step.
- **Parse Window** splits the window into *complete* CSV records (RFC 4180: quoted fields, embedded newlines, `""` escapes, CRLF/LF), maps + cleans each row, and packs rows into JSON batches of 2000. Whatever trails the last complete record is simply re-read at the start of the next window, so the only state carried between windows is an integer byte offset. Windows are decoded as latin1 (1 char = 1 byte) so offsets are exact and a multi-byte UTF-8 character cut by a window boundary can't be corrupted; each field is re-decoded to UTF-8 afterwards.
- **Insert Participants Batch** runs one statement per batch: the whole batch is a single `jsonb` parameter expanded server-side with `jsonb_populate_recordset`, `ON CONFLICT (row_hash) DO NOTHING`, and it returns how many rows were genuinely new — so `ingestion_log.rows_loaded` is real, not "rows extracted". A window's batches are sent to a database in one round trip, so a window lands there completely or not at all.
- **Summarize Window** folds the result into the loop state. When a file finishes (or fails) it attaches the file's result, which the parent turns into `ingest.ingestion_log` + `ingest.drive_file_state` rows.
- The mapping/cleaning rules are unchanged from the original (alias table + fuzzy-match suggestions, title-casing, `+254` phone normalisation, yes/no and gender normalisation, dedup by content hash). They now live in [`scripts/js/loader_parse_window.js`](../scripts/js/loader_parse_window.js). Behaviour differences worth knowing:
  - The literal text `null` in a CSV cell is treated as empty (the consolidated file uses it for every missing value; previously `national_id` would have been stored as the string `"null"`).
  - Unmapped columns are logged **once per file** (with a sample value), not once per cell, and `extra_json` omits keys whose value is empty. `ingestion_log.unmapped_column_count` therefore counts *columns*.
  - `pct_complete` is now an alias for `percent_complete`. The 23 source columns that used to fall into `extra_json` (`region`, `region_group`, `assistive_device`, `primary_language`, `employment_status`, `income_activity`, `monthly_income`, `internet_frequency`, `device_used`, `self_rated_digital_skill`, `cdc_name`, `cdc_phone`, `institution_level`, `trainer_level`, `course_taken`, `course_category`, `where_course_taken`, `date_trained`, `kictanet_cluster`, `has_device`, `internet_type`, `source`, `partner`) are now real `TEXT` columns of the same name, trimmed but otherwise stored as-is (nothing is guessed — e.g. `cdc_name` is *not* mapped onto `trainer_name`, `date_trained` is not parsed). Ten of them are empty in the consolidated file. They require [`0002_add_participant_source_columns.sql`](../sql/migrations/0002_add_participant_source_columns.sql) on the target database.
  - `source_file`, `drive_file_id` and the other identifier fields are no longer whitespace-collapsed by the cleaning pass.

## Import and set up

1. **Generate** (only needed after editing the script): `python scripts/build_data4_workflow.py`. This writes the portable files in `workflows/` (credential IDs are `REPLACE_ME` placeholders) and — if [`scripts/credential_ids.local.json`](../scripts/credential_ids.local.json) exists — wired copies in `workflows/local/` (gitignored) that reference your instance's credential IDs.
2. **Import** — command line (recommended; keeps the fixed workflow IDs the parent's *Load Chunk* node points at, and re-importing updates in place instead of creating another copy):
   ```
   docker exec n8nworkflow-n8n-1 mkdir -p /tmp/wf
   docker cp workflows/local/. n8nworkflow-n8n-1:/tmp/wf/
   docker exec n8nworkflow-n8n-1 n8n import:workflow --separate --input=/tmp/wf
   ```
   Use `workflows/` instead of `workflows/local/` if you don't have a local credentials file; you'd then assign credentials in the editor.
   Through the editor's *Import from file* instead, n8n assigns new IDs: import the loader first, then open **Load Chunk** in the ingestion workflow and re-select the loader from its dropdown.
3. **Migrate the target database — BEFORE importing.** [`0001_add_source_system.sql`](../sql/migrations/0001_add_source_system.sql) adds `source_system`; [`0002_add_participant_source_columns.sql`](../sql/migrations/0002_add_participant_source_columns.sql) adds the 23 source-file columns. Both are additive and instant. A database built from the current `sql/reporting_schema.sql` already has both; the Neon database has `source_system` but **not** the 23 columns yet. If you import first, every load fails cleanly with `column "region" of relation "participants" does not exist` (nothing is inserted).

   **Rows loaded before 0002** still hold those 23 values inside `extra_json`. Either (a) `TRUNCATE ingest.participants;` and re-run the workflow (a full reload, ~20–40 min; frees the space immediately — the safe choice on a storage-capped plan), or (b) run [`0003_backfill_participant_source_columns.sql`](../sql/migrations/0003_backfill_participant_source_columns.sql), which moves them in place. (b) rewrites every row and temporarily needs about the table's size in extra space — read the warning in the file first. Both give identical results (checked row-for-row on 59,382 rows).
4. **Credentials** (see the two setup sections below): Google Drive OAuth2 on **List Consolidated Data Files** *and* **Fetch Range (Google Drive)**; Microsoft OneDrive OAuth2 on **List OneDrive Files** *and* **Fetch Range (OneDrive)**; the **Pathways-Only PostgreSQL** credential on every Postgres node (one credential — there is one target database; see *Write target* below). Set `folderId` on **List OneDrive Files**.
5. **First run against a real database:** set `MAX_ROWS` in **Init Load State** to something small (e.g. `5000`), run, check `ingest.participants` / `ingest.ingestion_log`, then set it back to `0` and run the full load. The loader stops at the cap and says so in `error_message`. Re-running is safe — rows already loaded are skipped by `row_hash`.
6. The target is whichever database that credential points at (today: the Pathways-only Neon database). If you're unsure about a change, try it against a local sandbox first (see `docs/phase-1-setup.md`).

## Write target: one database (dual write is optional)

Every write goes to a single database: the one behind the **Pathways-Only PostgreSQL** credential — today the Pathways-only Neon database. Loading was originally dual-write (also to the shared ICTA+Pathways database, `icta_dashboard`); that was dropped because it doubled the load time and, when both credential slots pointed at the same database, wrote every log row twice.

To bring dual write back, generate with it switched on — `PATHWAYS_DUAL_WRITE=1 python scripts/build_data4_workflow.py` (PowerShell: `$env:PATHWAYS_DUAL_WRITE=1; python scripts/build_data4_workflow.py`) — which adds a `(Pathways DB)` twin of every write node. The plain-named nodes then use the **ICTA Reporting PostgreSQL** credential (the shared database, which needs `sql/migrations/0001_add_source_system.sql` applied first) and are the "primary": `ingestion_log.rows_loaded` counts the primary's inserts. In the loader the inserts are *chained* rather than parallel so **Summarize Window** runs exactly once per window; **Restore Batches** sits between them and re-reads the batches from **Parse Window**, so each database receives every batch of a window regardless of whether the other accepted it.

**Mark Dashboard Dirty** runs once per finished file that landed rows on the target database and bumps `app.dashboard_refresh_state.source_version` + `dirty_at`. It's only the "our side" half of dashboard refresh: nothing calls Superset itself yet (needs its URL and an API credential).

## Failure handling

- **A window can't be fetched** (revoked token → 401, no access → 403, file removed → 404, network) or **an insert fails**: the loader's HTTP and Postgres nodes are set to *continue on error*, so the failure is recorded instead of killing the run mid-file. The file gets an `ingestion_log` row with `status = 'failed'` and an `error_message` naming the node, the reason (e.g. `Insert Participants Batch: column "village" of relation "participants" does not exist`, or `Could not read bytes 0-8388607 of "…csv" from google_drive: …`), and the byte offset reached; `drive_file_state.last_status` is `failed` and the dashboard flag isn't bumped. Rows already committed stay committed; a re-run skips them via `row_hash` (it restarts from byte 0, it doesn't resume). (With dual write on, the error names which database's node failed, and a failure on one can leave the other holding that window — re-running reconciles them.)
- **A file whose header matches no canonical field** (blank/merged header, report-style export): skipped, logged as `header_not_detected` for manual review — nothing is inserted.
- **A source is unreachable** (bad/expired credential, missing folder): that source's list node has `onError: continueErrorOutput`; **Record Source Failure** tags it and **Check All Sources Failed** aborts the run only if *every* source failed, otherwise logs a `source_unreachable` row and carries on with the sources that worked. This was exercised end-to-end against a real n8n 2.35.5 with an unconfigured OneDrive credential — the run logged `source_unreachable` and still loaded the Drive file.
- **Server ignores `Range`** (would return the whole file for every window): detected (`got N bytes, asked for M`) and reported as a failure rather than silently reading the file repeatedly.

## Setting up the Google Drive OAuth2 credential

The Google Drive list node and **Fetch Range (Google Drive)** both use credential type `googleDriveOAuth2Api`. One-time setup:

1. **Google Cloud Console** (a free project is enough — no billing required for this quota level):
   - Create or pick a project at [console.cloud.google.com](https://console.cloud.google.com).
   - **APIs & Services > Library** — enable the **Google Drive API**.
   - **APIs & Services > OAuth consent screen** — set User type to **External** (unless this is a Google Workspace org, then **Internal**), fill in the app name/support email, and under **Test users** add the Google account that has access to the "Pathways Consolidated Data" Drive folder. This keeps the app usable without going through Google's verification review, since only test users can sign in to an unverified app.
   - **APIs & Services > Credentials > Create Credentials > OAuth client ID** — Application type **Web application**. Leave it open in this tab; you'll paste a redirect URI into it next.

2. **In n8n** (`http://localhost:5678` for the local Docker stack): **Credentials > New > Google Drive OAuth2 API**. n8n displays an **OAuth Redirect URL** on this screen — for the local Docker stack it's `http://localhost:5678/rest/oauth2-credential/callback`. Copy it into the Google Cloud OAuth client's **Authorized redirect URIs**, save the Google Cloud client, then copy its **Client ID** and **Client Secret** back into the n8n credential fields.

3. Click **Sign in with Google** in the n8n credential screen and authorize with the same Google account you added as a test user — the one that can already see the Pathways folder in Drive. The credential should show **Connected**.

4. Name the credential (e.g. `Google Drive - Pathways`) and save, then pick it on **List Consolidated Data Files** and **Fetch Range (Google Drive)**.

If you'd rather browse the folder by name than paste a raw ID into `filter.folderId`, also enable the **Google Picker API** in the same Cloud project — that's only needed for the "From list" browsing mode in n8n's UI, not for the workflow to run.

## Setting up the Microsoft OneDrive OAuth2 credential

The OneDrive nodes use `microsoftOneDriveOAuth2Api`. One-time setup (Azure AD / Microsoft Entra):

1. **Azure Portal** ([portal.azure.com](https://portal.azure.com)) → **Microsoft Entra ID > App registrations > New registration**.
   - Name it (e.g. "n8n Pathways OneDrive").
   - Supported account types: **Accounts in this organizational directory only** if the Pathways OneDrive is a work/school (Microsoft 365) account; pick a broader option only if it's a personal Microsoft account.
   - Redirect URI: type **Web**, value `http://localhost:5678/rest/oauth2-credential/callback` (same pattern as the Google Drive one, for the local Docker stack).

2. After registration:
   - **Certificates & secrets > New client secret** — copy the secret **value** immediately; it's only shown once.
   - **Overview** page — copy the **Application (client) ID**.
   - **API permissions > Add a permission > Microsoft Graph > Delegated permissions** — add `Files.ReadWrite.All` (`offline_access` and `openid` are typically included automatically). If your tenant requires admin consent for these permissions, click **Grant admin consent** (or ask whoever administers the tenant to do it) — without this, sign-in may succeed but file operations will fail with a permissions error.

3. **In n8n**: **Credentials > New**, search for **Microsoft Drive OAuth2 API** (that's the credential's actual display name in n8n, even though it's used for OneDrive). Paste the **Client ID** and **Client Secret** from the app registration, then **Sign in with Microsoft** using the account that owns/has access to the Pathways OneDrive folder.

4. Name the credential (e.g. `OneDrive - Pathways`) and save, then pick it on **List OneDrive Files** and **Fetch Range (OneDrive)**.

## Extending to a third source

A source is: a list node → **Tag Source: X** (must set `source_system` and normalise `modifiedTime` / `mimeType` / `parents`, and pass `size` through) → **Keep CSV or XLSX (X)** → **Init Load State**. Then in the loader, teach **Plan Request** how to build that source's download URL and add a **Fetch Range (X)** node beside the existing two (wired from **Which Source?**). Add the new source to **Check All Sources Failed** (`TOTAL_SOURCES`) with its own `onError` + **Record Source Failure** node.

## Extending the column mapping

The alias table lives in `ALIASES` at the top of [`scripts/js/loader_parse_window.js`](../scripts/js/loader_parse_window.js). As real files turn up headers it doesn't cover, add the normalised header text as an alias for the right canonical field, regenerate, and re-import. Anything that still doesn't match lands in `ingest.unmapped_columns_log` (once per file, with a fuzzy-match suggestion) and in `extra_json`, so nothing is lost.

To give a new source column its **own database column**: add it to `ALIASES` in the loader, to `PARTICIPANT_COLUMNS` in the build script, to `sql/reporting_schema.sql`, and write a migration (`ALTER TABLE ingest.participants ADD COLUMN IF NOT EXISTS … TEXT`) — and run that migration on the target database *before* importing the rebuilt workflows. The build script refuses to build if `ALIASES` and `PARTICIPANT_COLUMNS` disagree, so a field can't be silently dropped. Note that already-loaded rows are skipped on a re-run (the row hash covers raw source values, not the mapping), so a new column only fills for new rows unless you backfill or truncate-and-reload.

## Known limitations

- **XLSX is read whole**, not in windows (a workbook is a zip and can't be streamed): fine for small workbooks, but a huge one would still be held in memory by its sub-workflow run. Export very large sheets to CSV.
- Only the first sheet of a workbook is read, and `source_sheet` is always `null`.
- No incremental skip-if-unchanged logic yet — every run re-reads every file that passes the filter (`drive_file_state.last_modified_time` is recorded but not checked). Re-reads are cheap to reason about (idempotent) but not free: a full re-run of the consolidated file takes about as long as the first load.
- A failed file is not resumed from where it stopped; the retry starts at byte 0 (and skips already-loaded rows).
- `ingest.unmapped_columns_log` gets the file's unmapped columns re-logged on every run (23 rows per run for the consolidated file); the `resolved` flag is for manual triage, there's no de-duplication yet.
- Row identity is a 53-bit content hash (`row_hash`, unchanged from the original workflow), so two genuinely different rows colliding is possible in principle (odds are roughly 1 in 25,000 across ~870k rows); it did not happen in testing (825,177 distinct rows in, 825,177 hashes out).
- The OneDrive download path (`Fetch Range (OneDrive)`, Graph `/content` with a `Range` header) follows the same shape as the Google one but has not been run against a live OneDrive account.
- Dashboard auto-refresh is only half-built (see *Mark Dashboard Dirty* above).
- `ingest.drive_file_state`'s primary key is `drive_file_id` alone, not composite with `source_system` — accepted as a non-issue since Google Drive and OneDrive file ID formats aren't realistically going to collide (see the migration file's comment).
