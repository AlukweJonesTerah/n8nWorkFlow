# Data 1-4 + OneDrive ingestion workflow

[`workflows/data4-ingestion.json`](../workflows/data4-ingestion.json) is an importable n8n workflow implementing the MVP flow from the README against the real `ingest`/`app` schema, from two sources: Google Drive's Data 1-4 folders and a Microsoft OneDrive folder. It is generated by [`scripts/build_data4_workflow.py`](../scripts/build_data4_workflow.py) — edit that script and re-run `python scripts/build_data4_workflow.py` rather than hand-editing the JSON, so the SQL column lists and the JS parameter arrays that feed them can never drift out of sync. (The file/script names still say "data4" for historical reasons — it started as a Data-4-only test before growing to cover all four folders plus OneDrive.)

## What it does

Two parallel source branches, each list → tag → filter → limit → download, merge into one shared tail:

```
Manual Trigger -> Start Run ─┬─> List Data 1-4 Files -> Tag Source: Google Drive -> Keep CSV or XLSX -> Limit to 1 File -> Download File ─┐
                              └─> List OneDrive Files -> Tag Source: OneDrive -> Keep CSV or XLSX (OneDrive) -> Limit to 1 File (OneDrive) -> Download File (OneDrive) ─┤
                                                                                                                                                                        ├─> [Upsert Drive File State] + Is XLSX? -> Extract XLSX/CSV Rows
                                                                                                                                                                        -> Map Columns & Detect Unmapped -> Route By Record Type -> Insert Participant Row / Insert Unmapped Column Log / Insert Ingestion Log
```

- **List Data 1-4 Files** (Google Drive) lists all four Data folders in one Advanced Search query (`'<id>' in parents or ...` for each of Data 1-4's real folder IDs, hardcoded in `DATA_FOLDER_IDS`) — one node, one credential, instead of four separate branches. Each returned file's own `parents` field still says exactly which Data folder it came from. **List OneDrive Files** (Microsoft OneDrive) lists its one folder the same way the single-folder version worked before.
- **Tag Source: Google Drive** / **Tag Source: OneDrive** stamp `source_system` onto every item and normalize OneDrive's Graph API field names (`lastModifiedDateTime`, `file.mimeType`, `parentReference.id`) onto the same shape the Google Drive branch already uses (`modifiedTime`, `mimeType`, `parents`) — so every shared node downstream can stay source-agnostic.
- **Keep CSV or XLSX** (one per branch) drops anything that isn't a `.csv` or `.xlsx` file.
- **Limit to 1 File** (one per branch) caps each branch's first run to one file — the acceptance-test guard rail from `docs/phase-1-setup.md`. Delete or disable once that first run is verified, independently per branch.
- Both branches' **Download File** nodes feed the *same* **Upsert Drive File State** and **Is XLSX?** nodes — from here on, both sources share every remaining node.
- **Upsert Drive File State** writes/updates `ingest.drive_file_state` as a side branch, independent of the row-parsing path.
- **Is XLSX?** branches to the matching **Extract From File** node; both branches feed the same downstream node.
- **Map Columns & Detect Unmapped** (Code node) is where the real logic lives:
  - normalizes each source header and matches it against an alias table for the 37 canonical `ingest.participants` fields;
  - unmatched columns are kept (nothing is silently dropped) and get a fuzzy-match suggestion (Levenshtein-based) against the canonical field names;
  - computes a content-based `row_hash` per row so re-running the same file is idempotent (`ON CONFLICT (row_hash) DO NOTHING`);
  - emits one `ingestion_log` summary item per file (rows extracted, rows loaded, unmapped column count);
  - recovers which file/source each row came from by tracing `pairedItem` lineage back through a list of candidate "Tag Source" nodes (`SOURCE_TAG_NODES`) — `$('Node Name')` needs a literal name, so with two sources feeding this one node, it tries each candidate and catches the "not this item's ancestor" error from the ones that don't match. Adding a third source later means adding one more branch (list → tag → filter → limit → download) and one more line in `SOURCE_TAG_NODES`.
- **Clean & Transform Participant Data** (Code node) runs after Map Columns and only touches `_recordType === 'participant'` items (`unmapped_column`/`ingestion_log` items pass through untouched):
  - title-cases name/location fields (`full_name`, `county`, `sub_county`, `organization`, etc.);
  - normalizes `gender` and the yes/no fields (`disability`, `follow_up_consent`, `internet_access`) to consistent `Male`/`Female`/`Yes`/`No` regardless of how they were entered (`m`, `MALE`, `1`, `true`, ...);
  - normalizes Kenyan phone numbers (`phone_number`, `trainer_phone`) to `+254...` format from any of `07...`, `7...`, `254...`, `+254...` — anything that doesn't match one of those shapes is left as-is rather than forced;
  - strips non-digits from `national_id` (note: this would also strip letters from a passport number if one ever landed in that field — Kenyan national IDs are numeric, so this is a deliberate assumption, not an oversight);
  - strips `%` from `percent_complete`/`quiz_average`, and parses `completion_date`/`registration_date` into `YYYY-MM-DD` where parseable (kept as-is otherwise);
  - trims and collapses whitespace on every other string field, without forcing casing (so free text like `remarks` and identifiers like `serial_no`/`username` aren't mangled).
  - Runs *after* `row_hash` is computed in Map Columns, deliberately — so changing a cleaning rule later doesn't retroactively change the dedup key for rows already loaded.
- **Route By Record Type** (Switch) sends each emitted item to the matching Postgres insert — and now *every* insert is duplicated across two databases (see below).

## Dual-write: shared DB + Pathways-only DB

There are two target databases, both fed from the same `Route By Record Type` outputs (and both copies of `Upsert Drive File State` fed by both `Download File` nodes, and both copies of `Insert Ingestion Log` also fed by `Check All Sources Failed`):

- **ICTA Reporting PostgreSQL** — the shared ICTA+Pathways database (`icta_dashboard`), the one we already have real credentials for and have been testing against all along.
- **Pathways-Only PostgreSQL** — a new, Pathways-only database that doesn't exist yet / has no real credentials yet. For MVP this points at a new local sandbox, `postgres-pathways` in `compose.yaml` (mirrors the same `ingest`/`app` schema via the same `sql/reporting_schema.sql`). Swap in real credentials once the team provisions this database — nothing else about the workflow needs to change.

Every one of the four write nodes (`Upsert Drive File State`, `Insert Participant Row`, `Insert Unmapped Column Log`, `Insert Ingestion Log`) has a `(Pathways DB)` twin using the identical query — same `build_upsert_from_pairs`/`build_insert` output, just a different `credentials` block — so the two databases can never drift out of sync in what they receive.

**Mark Dashboard Dirty** runs once per successful run, right after `Insert Participant Row` (the shared-DB copy only, since that's what the dashboard reads), and bumps `app.dashboard_refresh_state.source_version` + sets `dirty_at = now()`. This is only the "our side" half of the "dashboard refreshes automatically" requirement — it updates the bookkeeping table the schema already had sitting unused, but doesn't yet call Superset itself. That needs Superset's base URL and an API credential (or at minimum, confirmation Superset is even pointed at `ingest.participants` yet) before it can be wired up.

## Source failure fallback

If one source is unreachable (revoked OAuth token, deleted/renamed folder, network error), the pipeline still ingests from whichever source *is* reachable, and only aborts the whole run if **neither** source works:

- **List Data 1-4 Files** and **List OneDrive Files** both have `onError: continueErrorOutput` set — instead of aborting the workflow, a failing node gets a second output specifically for the error, wired to **Record Source Failure: Google Drive** / **Record Source Failure: OneDrive**. These extract a human-readable reason from whatever shape the error comes in (`item.error`, `item.json.error`, or a raw message) and tag it with which source failed.
- Both failure nodes feed **Check All Sources Failed**. This node only actually executes when at least one source failed — a node with zero items on every input isn't run, so the normal "both sources fine" case never touches this path.
  - If it receives failures from **every** source (currently `TOTAL_SOURCES = 2`), it throws, which aborts the whole run with a message naming every source and its specific reason (e.g. `All 2 sources failed, nothing to ingest this run — google_drive: <reason> | microsoft_onedrive: <reason>`).
  - If fewer than all sources failed, it logs a `source_unreachable` row per failed source straight into `ingest.ingestion_log` (bypassing the row-mapping path entirely, since there's nothing to map) and lets the run continue with whatever succeeded.
- Adding a third source means adding its own `onError` + `Record Source Failure` node feeding into `Check All Sources Failed`, and bumping `TOTAL_SOURCES` in `CHECK_ALL_SOURCES_FAILED_JS`.

**Not yet independently verified against a live failure** (unlike everything else in this workflow, which has been tested node-by-node against real data): n8n's `continueErrorOutput` behavior is well-documented for per-item errors within a node that's already processing items, but its exact behavior when a node fails entirely before touching any items — e.g. an expired OAuth token, which is a whole-node failure, not a per-item one — has some nuance in n8n's own execution engine I could not fully confirm by reading the source alone. Trigger a real auth failure (e.g. revoke/expire one credential) and confirm the error actually lands on **Record Source Failure**'s input rather than skipping straight past it, before relying on this in production.

## Before running

1. **Run the migration** — [`sql/migrations/0001_add_source_system.sql`](../sql/migrations/0001_add_source_system.sql) adds the `source_system` column this version needs, against **both** Postgres targets (whichever local sandbox and/or the shared remote `icta_dashboard` you're pointing at). It's additive and safe (both tables are currently empty).
2. **Shared DB credential** — create one named `ICTA Reporting PostgreSQL` using the real host/port/database/user/password from the team (SSL: disable), and assign it on every Postgres node whose name does *not* say "(Pathways DB)".
3. **Pathways-only DB credential** — create a second one named `Pathways-Only PostgreSQL`. No real credentials exist yet, so for now point it at the new local `postgres-pathways` container (`docker compose up -d` brings it up alongside the others). Assign it on every node whose name *does* say "(Pathways DB)".
4. **Google Drive credential** — create/select an OAuth2 Google Drive credential on both Google Drive nodes. See below for the one-time Google Cloud setup.
5. **OneDrive credential** — create/select a Microsoft OneDrive OAuth2 credential on both OneDrive nodes. See below for the one-time Azure setup.
6. **Folder IDs** — **List Data 1-4 Files** already has Data 1-4's real folder IDs baked into its query, nothing to edit there. Open **List OneDrive Files** and replace `folderId` (`REPLACE_WITH_ONEDRIVE_FOLDER_ID`) with the real OneDrive folder ID (or `root` for the drive's top level).
7. Test against the local `postgres-reporting` sandbox (see `docs/phase-1-setup.md`) before pointing the shared-DB credential at the real remote database, since `ingest`/`app` there hold the team's real (currently empty) tables.

## Setting up the Google Drive OAuth2 credential

The workflow's two Google Drive nodes are configured for `authentication: oAuth2` with credential type `googleDriveOAuth2Api`. One-time setup:

1. **Google Cloud Console** (a free project is enough — no billing required for this quota level):
   - Create or pick a project at [console.cloud.google.com](https://console.cloud.google.com).
   - **APIs & Services > Library** — enable the **Google Drive API**.
   - **APIs & Services > OAuth consent screen** — set User type to **External** (unless this is a Google Workspace org, then **Internal**), fill in the app name/support email, and under **Test users** add the Google account that has access to the "Pathways Consolidated Data" Drive folder. This keeps the app usable without going through Google's verification review, since only test users can sign in to an unverified app.
   - **APIs & Services > Credentials > Create Credentials > OAuth client ID** — Application type **Web application**. Leave it open in this tab; you'll paste a redirect URI into it next.

2. **In n8n** (`http://localhost:5678` for the local stack): **Credentials > New > Google Drive OAuth2 API**. n8n displays an **OAuth Redirect URL** on this screen — for the local Docker stack it's `http://localhost:5678/rest/oauth2-credential/callback`. Copy it into the Google Cloud OAuth client's **Authorized redirect URIs**, save the Google Cloud client, then copy its **Client ID** and **Client Secret** back into the n8n credential fields.

3. Click **Sign in with Google** in the n8n credential screen and authorize with the same Google account you added as a test user — the one that can already see the Pathways folder in Drive. The credential should show **Connected**.

4. Name the credential (e.g. `Google Drive - Pathways`) and save. Then open **List Data 1-4 Files** and **Download File** in the imported workflow and pick this credential from the dropdown — the placeholder `REPLACE_ME` id in the JSON won't auto-resolve to it.

If you'd rather browse the folder by name than paste a raw ID into `filter.folderId`, also enable the **Google Picker API** in the same Cloud project — that's only needed for the "From list" browsing mode in n8n's UI, not for the workflow to run.

## Setting up the Microsoft OneDrive OAuth2 credential

The workflow's two OneDrive nodes are configured for `authentication: microsoftOneDriveOAuth2Api`. One-time setup (Azure AD / Microsoft Entra):

1. **Azure Portal** ([portal.azure.com](https://portal.azure.com)) → **Microsoft Entra ID > App registrations > New registration**.
   - Name it (e.g. "n8n Pathways OneDrive").
   - Supported account types: **Accounts in this organizational directory only** if the Pathways OneDrive is a work/school (Microsoft 365) account; pick a broader option only if it's a personal Microsoft account.
   - Redirect URI: type **Web**, value `http://localhost:5678/rest/oauth2-credential/callback` (same pattern as the Google Drive one, for the local Docker stack).

2. After registration:
   - **Certificates & secrets > New client secret** — copy the secret **value** immediately; it's only shown once.
   - **Overview** page — copy the **Application (client) ID**.
   - **API permissions > Add a permission > Microsoft Graph > Delegated permissions** — add `Files.ReadWrite.All` (`offline_access` and `openid` are typically included automatically). If your tenant requires admin consent for these permissions, click **Grant admin consent** (or ask whoever administers the tenant to do it) — without this, sign-in may succeed but file operations will fail with a permissions error.

3. **In n8n**: **Credentials > New**, search for **Microsoft Drive OAuth2 API** (that's the credential's actual display name in n8n, even though it's used for OneDrive). Paste the **Client ID** and **Client Secret** from the app registration, then **Sign in with Microsoft** using the account that owns/has access to the Pathways OneDrive folder.

4. Name the credential (e.g. `OneDrive - Pathways`) and save. Then open **List OneDrive Files** and **Download File (OneDrive)** and pick this credential from the dropdown.

## Extending to a third source

Each source is: `List <Source> Files -> Tag Source: <Source> -> Keep CSV or XLSX (<Source>) -> Limit to 1 File (<Source>) -> Download File (<Source>)`, feeding into the *same* `Upsert Drive File State` and `Is XLSX?` nodes everything else already shares. The `Tag Source` node is what makes the shared tail possible — it must set `source_system` and normalize field names (`modifiedTime`, `mimeType`, `parents`) to match what `Upsert Drive File State`'s query expects, whatever shape the new source's API actually returns. Then add one line to `SOURCE_TAG_NODES` in `MAP_COLUMNS_JS` (in `scripts/build_data4_workflow.py`) pointing at the new `Tag Source` node's name, so `Map Columns & Detect Unmapped` can recover that source's rows too.

## Extending the column mapping

The alias table lives in `ALIASES` inside `scripts/build_data4_workflow.py` (`MAP_COLUMNS_JS`). As real files turn up headers this list doesn't cover, add the normalized header text as a new alias for the right canonical field, then regenerate the workflow JSON and re-import it. Anything that still doesn't match lands in `ingest.unmapped_columns_log` with a fuzzy-match suggestion rather than being lost, so nothing needs to be perfect before the first run.

## Known limitations of this first version

- No incremental skip-if-unchanged logic yet — every run re-reads every file that passes the filter (`ingest.drive_file_state.last_modified_time` is recorded but not yet checked before downloading).
- `source_sheet` is always `null` — the workflow reads each file's first sheet only.
- Not yet wired to a schedule trigger; still manual per the Phase 1 acceptance test.
- No dashboard-facing view yet (see `docs/phase-1-setup.md`).
- Dashboard auto-refresh is only half-built: `app.dashboard_refresh_state` gets bumped, but nothing calls Superset's own refresh/cache-invalidation API yet — needs Superset's URL and an API credential.
- `ingest.drive_file_state`'s primary key is `drive_file_id` alone, not composite with `source_system` — accepted as a non-issue since Google Drive and OneDrive file ID formats aren't realistically going to collide as the same string (see the migration file's comment).
